IMPLEMENTATION NOTE · 2026-10-29

SBCL 上の selective CPS による
shift / reset

単一 prompt、多重呼出し、合成的継続。Asai–Uehara の純粋性注釈に基づく考え方を、動的型付けの Common Lisp へ保守的に適用する。

保証の範囲。ここに記すのは実装の操作的仕様と設計上の意味保存の根拠であり、この CL 実装全体の機械検証ではない。論文の answer-type 多相型推論器そのものを実装したという主張も行わない。未変換の native スタックを捕捉しないという適用範囲を明示する。

1. 基準となる意味論

コアは call-by-value の λ 計算へ Danvy–Filinski の shift/reset を加えたものとする。\(v\) は値、\(E\) は reset を含まない評価文脈である。Common Lisp では関数適用を funcall で表し、引数を左から右へ評価する。

\[ \begin{aligned} e &::= v \mid e\;e \mid \langle e\rangle \mid \mathcal S k.e\\ E &::= [\,] \mid E\;e \mid v\;E \end{aligned} \]
\[ \begin{aligned} (\lambda x.e)\;v &\longrightarrow e[v/x],\\ \langle v\rangle &\longrightarrow v,\\ \langle E[\mathcal S k.e]\rangle &\longrightarrow \left\langle e\left[(\lambda x.\langle E[x]\rangle)/k\right]\right\rangle. \end{aligned} \]

最後の規則で継続の本体に再び reset がある点が本質である。取得した継続の呼出しは呼出し元へ値を返し、その再開中の shift には新しい delimiter が見える。単発の非局所脱出、abortive な call/cc、control/prompt を代用しない。

(reset (+ 1 (shift k (+ (funcall k 10) (funcall k 20)))))
;; => 32

(let ((k (reset (+ 10 (shift k k)))))
  (list (funcall k 2) (funcall k 7)))
;; => (12 17)

2. 注釈と selective CPS

制御効果の注釈は \(p\leq i\) の２点とする。\(p\) は直接実行できることを意味し、参照透過性は意味しない。副作用を持つ rplaca 等も制御を捕捉しなければ直接実行できる。

\[ \begin{aligned} \epsilon_{\mathrm{sub}} &\leq \epsilon_{\mathrm{parent}},\\ \epsilon_{\mathrm{body}(f)} &\leq \epsilon_{\mathrm{latent}(f)},\\ \epsilon_{\mathrm{latent}(f)} &\leq \epsilon_{\mathrm{call}(f)},\\ \epsilon_{\mathcal S k.e} &= i,\qquad \epsilon_{\langle e\rangle}=p. \end{aligned} \]

不明な関数呼出しは \(i\) から開始する。既知の CL プリミティブの安全な呼出しは \(p\) とし、ローカル関数の呼出しはその latent effect に依存させる。optional/key/aux の初期化式も関数の効果へ加える。再帰的な labels の制約は単調な不動点計算で解く。関数値の生成と、その本体を呼び出した場合の効果を区別する。

Common Lisp の動的制御形式は、必要なら保守的に CPS 側へ置く。捕捉や領域外への脱出を含む block/tagbody、および special 束縛にはランタイムのフレームが必要である。reset はその内部の制御効果を外へ伝えず、制御効果のある body には独立した trampoline と prompt を作る。body も純粋なら、その生成を省略して直接実行する。

論文との対応この実装
pure / impure の注釈による選択的変換制約で分類した direct 部分を native Lisp として生成する。
関数型上の latent effectローカルな名前付き関数に latent effect を持たせ、動的な関数値は保守的に CPS 呼出しする。
answer type を含む多相型推論実装しない。動的型付けを保ち、native/CPS の関数値を実行時に橋渡しする。
型の異なる関数表現の整合CPS 関数を SB-MOP の funcallable object として表し、native 関数と呼出し口を共通化する。
論文の正当性定理・Agda 検証参考にするが、この CL 拡張へその定理をそのまま適用したとは主張しない。

3. ヒープ上の継続と新しい prompt

ランタイムの継続は不変のフレーム列である。\(P\) を最も近い prompt、\(R\) をそれより外側とする。

\[ K=F_1::\cdots::F_n::P::R, \qquad \Gamma=[F_1,\ldots,F_n]. \]

shift は \(\Gamma\) を保存し、\(P\) までの動的領域を退出してから body を実行する。取得した継続を値列 \(\vec v\) で呼ぶと、呼出し元の継続 \(C\) の上へ新しい prompt とフレーム列のコピーを置く。

\[ \operatorname{invoke}(\Gamma,\vec v,C) =\operatorname{resume}\bigl( \operatorname{copy}(\Gamma)\mathbin{+\!+}[P_{\rm fresh}]\mathbin{+\!+}C, \vec v\bigr). \]

フレームの spine を複製し、保存済みの spine を破壊しない。通常のフレームの処理関数は、古い継続末尾を閉包へ埋め込まず、明示的な next 引数を受け取る。字句変数のロケーションや special の束縛セルは共有する。従って継続の多重呼出しはストアを巻き戻さず、既に評価した引数や副作用を最初から再実行もしない。

4. 多値と評価順序

内部の戻り値は長さゼロを許す値列 \(\vec v=(v_1,\ldots,v_m)\) である。関数引数・条件式・setq の RHS 等の単一値文脈では次の射影を行う。

\[ \operatorname{primary}(\vec v)= \begin{cases}v_1 & m>0,\\ \mathrm{nil} & m=0.\end{cases} \]

multiple-value-call は各引数式の値列を順に連結する。multiple-value-prog1 と unwind-protect の正常復帰では元の値列を保持する。継続の引数もこの値列なので、(funcall k) と (funcall k 1 2 3) の両方を扱える。

評価済みの引数は各々の字句的な一時変数に保持する。後続の引数で shift が生じても、先行する引数式を再評価したり、後で変化した場所を読み直したりしない。

5. 動的領域と保留中の制御遷移

special / progv の束縛、catch、block、tagbody、cleanup、dynamic-wind をフレームとして持つ。各 task は自身の継続フレームが表す special 束縛の下で実行される。native な symbol-value、setq、makunbound の結果を束縛セルへ同期する。

移行元と移行先の共通末尾を計算し、退出する領域の cleanup/after を内側から外側へ実行する。再入する wind の before は外側から内側へ実行する。cleanup は共有される可変の「使用済み」フラグで単発化しない。

cleanup や before 自身から shift する場合、保留中の移行先まで継続の一部になる。このため移行先は不透明な閉包に隠さず、transfer-goal / entry-state のデータとして保持する。フレーム複製時に移行先と prompt の対応も付け替える。元の reset の外にある、失効した block 等を復活させることはない。

(reset
  (let ((first t))
    (+ 10 (unwind-protect (shift k (funcall k 1))
            (when first
              (setf first nil)
              (shift h (+ 100 (funcall h 0))))))))
;; => 111  (cleanup 中の捕捉も合成的)

direct 側の reset と CPS 側の呼出しが別の driver に属する場合、return/go/throw はまず現在の driver の仮想的な動的領域を退出し、それから native の脱出を行う。これにより native アンワインドの開始前には、cleanup 内の shift も通常どおり扱える。

6. native 境界

未変換関数の戻り先はヒープ上にない。その内部から外側の prompt へ継続を捕捉することはできない。CPS 関数の native な呼出し口は、暗黙の reset を作らない独立した driver を使い、外側まで捕捉しようとすれば native-boundary を通知する。callee 内の明示的な reset で完結する操作は可能である。

map 系、reduce、some/every 等の同梱アダプタは callback の戻り先もヒープ上へ置く。新しい関数には register-cps-adapter で同じ呼出し規約を持つ変換済みの実装を登録できる。

未処理の native エラー等によって既に始まった native アンワインドも境界である。その際の cleanup から元の prompt へ捕捉する要求を拒否し、成功したかのように計算を進めない。独立した新しい reset 内での捕捉は許す。

単一 prompt のコア意味論を実装する範囲と、未変換 Common Lisp 全体との透過的相互運用を区別する。後者について無制限の互換性を主張しない。ローカル型宣言を観測する独自マクロなど、詳細な制約は README を参照されたい。

1.1 の最適化

純粋な引数列を左から右へ通常の let* で評価し、その値を字句的な一時変数へ保持する。単一値文脈では CL の通常の評価が第１値を取り、値がなければ nil とする。したがって、直接実行する部分をまとめても、後続の shift や代入によって先行する引数を読み直すことはない。progv が必要な領域では適切な束縛を設定した task の内部で直接評価する。

block と tagbody の領域効果を、その本体・return-from/go と相互に制約する。効果が純粋な閉じた領域は native な block/tagbody として生成する。関数または reset の境界をまたぐ参照は保守的にヒープ上の対象へ昇格させ、元の対象の失効検査を維持する。

継続の共通末尾は不変・非循環のフレーム列の長さを合わせて探索する。複製対象が保留中の制御移行を含まなければ mapping を省略する。transition/enter フレームを含む場合の移行先の付け替えは元の経路を使う。動的環境、cleanup、多重呼出しの規約を省略する最適化ではない。

7. 検証

コンパイラとは独立した簡約器は、βv と上記 shift/reset 規則を捕獲回避置換で直接実行する。コンパイラ IR、ランタイムフレーム、CPS evaluator を使わない。
